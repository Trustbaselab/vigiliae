# 领域 Master 构建法

## 何时使用

- 要把一个垂直行业的专业知识封装成 Agent
- 现有 Agent 只做后台支撑（监控/采集/记账），用户用不上
- 要从「查数据」升级到「给专业判断」
- 要给一个行业做「用户说一句话就完成」的产品

**不适用**：

- 只做通用问答 → 不需要领域 Master
- 只做数据查询 → 用 MCP/工具即可

---

## 核心区别：职能 Agent vs 领域 Master

这一条决定了产品能不能被用户用起来。

| 类型 | 例子 | 用户能直接用吗 |
|---|---|:-:|
| **职能 Agent**（后台工蜂） | 心跳探针、采集器、记账员、验证器 | ❌ 看不见 |
| **领域 Master**（前台专家） | 「材料专家」「合规专家」「选型专家」 | ✅ 一句话完成 |

**⭐ 一支舰队应该两种都有：**
```
后台：N 个工蜂负责采集/监控/验证/记账（保障数据可靠）
前台：M 个 Master 负责接客（用户直接对话）

⭐ 只有工蜂 = 用户看不见（跑得再勤也没用）
⭐ 只有 Master = 没有数据支撑（答得再顺也是空话）
```

## 执行流程（六步）

### ① 定义「业务对象」（语义层的地基）

**⭐ 这一步决定了这个 Master 聪不聪明。做错了后面全错。**

把行业里**真实存在、有名字、能指认**的东西列出来：

```
❌ 错：列「数据表」「字段」「API」
✅ 对：列「客户能指着说这是什么」的东西

例（rCB 行业）：
  牌号 / 厂商 / 生产线 / 检测方法 / 认证 / 政策 / 价格区间 / 废料来源
例（碳行业）：
  产品 / 工艺路线 / 核算边界 / 排放因子 / 认证方案 / 申报义务
```

**验收标准：一个行业老兵看到这个列表，会说「对，我们平时就是这么说的」。**

### ② 定义「对象之间的关系」（这决定 Master 能不能推理）

**⭐ 关系比属性更重要。属性只能查，关系才能推理。**

```
例（rCB）：
  牌号 --[可替代]--> 牌号        （带替代比例上限）
  牌号 --[检测用]--> 检测方法     （带 ASTM 编号）
  牌号 --[生产于]--> 厂商
  牌号 --[受管制]--> 政策/法规
  厂商 --[位于]--> 地区

⭐ 有了关系，用户问「这个牌号能替代 N550 吗、要测什么、出口要注意什么」
   才能串成一条推理链，而不是三次独立查询。
```

### ③ 圈定「可信数据源」（决定答案敢不敢用）

每个对象都要有明确的数据来源和可信等级：

```
| 对象 | 一手源 | 二手源 | 允许标 A 的条件 |
| 牌号 | 厂商官网 datasheet | 论文/行业媒体 | 厂商官方文件 + 逐字 quote |
| 政策 | 政府/法规官网 | 律所解读 | 官方原文可访问 |
| 价格 | —— | 交易市场/行业报价 | ⚠️ 价格永远不给单点数字 |
```

**⭐ 没有一手源的对象，答案必须降级披露，不能装成确定。**

### ④ 设计「判断规则」（Skill 形态，不是 prompt 形态）

**⭐ 这是 Master 和「普通聊天机器人」的分水岭。**

判断规则要写成**可执行的判据**，不是模糊描述：

```
❌ 弱：「根据参数综合判断牌号」
✅ 强：
   ① 先看灰分：>X% → 判为再生
   ② 再生则看甲苯透光率 + 无机物含量 → 定 R 码
   ③ 原生则看碘值/DBP/粒径 → 定 N 牌号
   ④ 缺任一关键参数 → 明确说「无法判定」，不猜
```

**⭐ 判断规则应该独立成 Skill 文件，可被审计、可被复用、可被版本管理。**

### ⑤ 配置「输出与动作」

Master 的输出不能只是「一段话」，要能变成下一步动作：

```
输出层次：
  L1 结论（这是什么）
  L2 依据（凭什么这么判，带 source_url）
  L3 待验证项（哪些还不确定，要怎么验）
  L4 建议动作（下一步做什么，谁做）
  L5 可交付物（可下载的报告/建议书）
```

**⭐ 只做到 L2 = 顾问；做到 L4-L5 = 参与者。**

### ⑥ 建「评测集」（决定你能不能证明它靠谱）

**⭐⭐ 这是最容易被忽略、但最值钱的一步。**

```
评测集 = 一批「问题 + 标准答案 + 判定依据」

例（rCB 牌号判定）：
  输入：碘值 45 / DBP 120 / BET 42 / 灰分 0.8%
  标准答案：N660
  依据：ASTM D1765 该区间
  可接受误差：相邻牌号不算错（需说明）

规模建议：每类任务 50-100 条即可起步
```

**⭐ 有评测集才能：**
```
① 换模型时验证能力有没有退化
② 对外证明「这个 Master 在这个领域 X% 准确」
③ 招人/合作时有客观基准
④ 大厂做不了（他们不懂这个行业的标准答案）
```

## Master 的 prompt 骨架

```
你是【行业】的【角色】专家。

## 你能回答的问题类型
【列出 3-5 类用户真实会问的问题】

## 你的判断依据
【引用对应的 Skill 判断规则】

## 你的数据来源
【MCP 工具清单 或 数据接口】

## 输出格式（必须）
① 结论（一句话，先说答案）
② 依据（带 source_url / 标准编号）
③ 不确定的地方（明确列出）
④ 建议动作（谁做什么）
⑤ 局限（什么情况下这个结论不成立）

## 硬规则
- 数据不足时明确说「无法判定」，不猜
- 不给没有来源的数字
- 价格类只给区间不给单点
- 涉及法规必须注明版本和生效日期
```

---

## 验收清单

一个领域 Master 算不算建成，过这 8 条：

```
□ 业务对象列表，行业老兵认可
□ 对象之间的关系 ≥ 5 种
□ 每个对象都有可信数据源
□ 判断规则独立成 Skill，可审计
□ 输出到 L4（建议动作）
□ 有 ≥ 50 条评测集
□ 数据不足时会明确说「不知道」
□ 用户不用懂内部结构，一句话就能用
```

---

## 诚实边界

- 本 Skill 是构建方法，不含任何行业数据或规则
- 评测集的「标准答案」必须由行业专家确认，**不能由构建者自己定**
- Master 的准确率只能说「在 N 条评测集上 X%」，**不能外推为「全面可靠」**
- 涉及法规/安全/健康的判断，必须保留「最终由人决定」的免责边界
- 不要为了「显得聪明」而隐藏不确定性——**明确说不知道比编一个答案有价值**
