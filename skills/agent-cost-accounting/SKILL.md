# Agent 成本核算

## 何时使用

- 多 Agent 系统开始产生 API 账单，但不知道钱花在哪
- 要做成本看板、预算红线、余额预警
- 要判断「加一个 Agent」的边际成本
- 模型/配置变更后要验证成本有没有失控

**不适用**：

- 单一脚本的一次性成本 → 直接看账单
- 要判断「这钱花得值不值」→ 用 `agent-efficiency-audit`

---

## 第一原则：没有 token 计量也能算清

**多数 Agent 编排框架不暴露 token 用量。别指望它，用余额差值。**

```
❌ 常见做法（不准）：
   看输出长度 × 单价  → 漏掉输入（输入通常比输出大 5-10 倍）

✅ 正确做法（准）：
   每 N 分钟查一次账户余额
   两次余额差 = 这段时间真实花费
   按该时段各 Agent 的调用次数分摊
```

**⭐ 这个方法的优点：**

| 优点 | 说明 |
|---|---|
| 100% 真实 | 不是估算，是账单本身 |
| 零成本 | 一次 HTTP 查询，不消耗 token |
| 不依赖框架 | 任何 API 计费系统都适用 |
| 含全部开销 | 输入、输出、缓存、重试全算进去 |

**⭐ 缺点（必须承认）：**

```
· 只能给「窗口级」精度，不能精确到单次调用
· 按调用次数分摊是「假设各次成本相近」，实际有偏差
· 若窗口内有非 Agent 消耗（人工测试、其他应用），会算进来
```

## 执行流程（六步）

### ① 先测「单次调用基线」

**⭐ 这是所有后续判断的锚点。不测基线，后面全是猜。**

```
方法：
1. 记录余额 B1
2. 发起 1 次最简单的调用（如「回答一个字」）
3. 记录余额 B2
4. 单次基线 = B1 - B2

⚠️ 要扣掉同期其他消耗（若有定时任务在跑，先停或选空窗期）
```

**实测参考（某系统，deepseek 系模型）：**
```
最简单调用（单次、无工具）:  ¥0.05-0.10
带 5-10 轮工具调用的 Agent:  ¥0.20-0.50
读全量数据集的重型 Agent:    ¥1-3
```

**⭐ 基线必须定期重测**——模型调价、提示词变长、工具增加都会变。

### ② 建窗口差值采集

```
每 30 分钟（或 15 分钟）执行：
  ① 查当前余额 → bal_now
  ② 读上一条记录 → prev.balance
  ③ 花费 = prev.balance - bal_now
     （负数 = 充值，记为 0）
  ④ 统计窗口内各 Agent 的调用次数
  ⑤ 按次数分摊
```

**⚠️ 三个必须处理的边界情况：**

| 情况 | 处理 |
|---|---|
| 余额上升（充值） | 记为 0，不记负花费 |
| 窗口内无调用但有钱减少 | 标 `unattributed`，说明有非 Agent 消耗 |
| 首次运行（无上一条） | 只记基线，不算花费 |

### ③ 按调用次数分摊（并标注误差）

```
Agent A 花费 = 窗口总花费 × (A 的调用次数 / 总调用次数)

⚠️ 这个分摊假设「各次调用成本相近」。
   如果一个窗口里既有轻量 Agent 又有重型 Agent，分摊会失真。
```

**⭐ 改进方法（二阶精度）：**

```
给每个 Agent 一个「权重」而不是次数：
  权重 = 该类调用的实测成本 / 基线成本

例：普通 vigiliae 权重 1.0，重型 sator 权重 8.0
   A 花费 = 总花费 × (A 的加权次数 / 总加权次数)
```

### ④ 成本归一化（这是关键指标）

**⭐ 光看「花多少」没意义，要看「每单位产出花多少」。**

| 业务 | 分母 | 指标 |
|---|---|---|
| 数据采集 | 条有效记录 | ¥/条（含 A/B/E 分级） |
| 判定服务 | 次判定 | ¥/次 |
| 监控 | 小时 | ¥/小时 |
| 报告 | 份 | ¥/份 |

**⭐ 归一化之后才能比较：**
```
Agent A 花 ¥50 产出 500 条   → ¥0.10/条  ✅
Agent B 花 ¥30 产出 5 条     → ¥6.00/条  ❌ 有问题
```

### ⑤ 设预算红线

```
三档阈值（按日预算的百分比）：
  70%  → 提醒（在预算内，但注意）
  90%  → 告警（要降频或停非关键 Agent）
  100% → 硬停（自动禁用非核心 Agent）
```

**⭐ 余额预警同理：**
```
余额 < 7 天消耗  → 提醒充值
余额 < 3 天消耗  → 告警
余额 < 1 天消耗  → 硬停非核心
```

### ⑥ 输出成本看板

**必须能回答这五个问题：**

```
① 今天花了多少？（当前值 + 趋势）
② 哪个 Agent 最烧钱？（排名）
③ 余额还能用几天？（预测）
④ 哪类任务单位成本最高？（归一化排名）
⑤ 有没有「花了钱但没产出」的？（异常项）
```

## 频率设计：先算成本，再定频率

**⭐ 这是最容易被忽略的因果。**

```
例：某 Agent every:300（288 次/天）
    单次成本 ¥0.10
    日成本 = ¥28.8
    
    若日预算只有 ¥20 → 必须降到 every:600 或更低
    
⭐ 正确顺序：
   ① 测单次成本
   ② 定日预算
   ③ 反算允许的频率
   ④ 再设 schedule
   
❌ 错误顺序：先定频率，再发现超预算
```

---

## 成本优化手段（按性价比排序）

| 手段 | 省多少 | 代价 |
|---|:-:|---|
| **降频**（every:300 → every:600） | 50% | 响应变慢 |
| **按需触发**（schedule="" 只手动） | 90%+ | 要人介入 |
| **换轻模型** | 60-80% | 质量下降 |
| **拆任务**（重型拆成多次轻量） | 30-50% | 实现复杂 |
| **加缓存**（相同问题不重复调） | 20-40% | 命中率不定 |
| **压缩提示词**（减少固定开销） | 10-30% | 要持续维护 |
| **批量处理**（多次合并成一次） | 20-50% | 时效性下降 |

**⭐⭐ 最有效的永远是「降频」和「按需触发」——不要为了「看起来实时」而浪费钱。**

## 常见陷阱

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 用输出长度估成本 | 低估 5-10 倍（漏掉输入） | 用余额差值 |
| 没测基线就设预算 | 预算和实际完全对不上 | 先测单次基线 |
| 只看总花费不看单位成本 | 贵但没产出也看不出来 | 做归一化 |
| 定时任务频率 > 配额 | 每天都有「假失败」 | 先反算频率上限 |
| 余额查太频繁 | 浪费请求 | 15-30 分钟一次足够 |

---

## 诚实边界

- 余额差值法的精度受「非 Agent 消耗」污染，无法区分
- 按次数分摊是近似值，**不能对外说「某 Agent 精确花了 X 元」**
- 单价会变（模型调价、缓存策略变、供应商变），基线要定期重测
- 归一化指标需要「产出质量」定义，否则会激励「多产低质」
- 本 Skill 不含任何具体价格，实际单价以供应商当期价目为准
